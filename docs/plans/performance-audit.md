# 性能与结果处理审查（DS + 独立复核）

审计基线：`1f9316a8204430dc5660ce403b885ae151c20fbd`。初次审计阶段仅研究、验证和记录；后续获准实施的第一批修复见第 7 节。第 7 节为提交与部署前的实施验证快照；发布状态以 Git 提交及 Actions 运行结果为准。

复核状态：DS 的链路发现由主审独立复现/收紧；本报告经 DS 只读交叉复核通过，无阻塞项。

## 1. 范围、证据与结论边界

- DS 走读请求、轮询、取消、任务队列、历史与图片存储；主审走读主页面渲染、Workflow、标签索引、图片与资源库前端，双方交叉复核。
- 额外查看了统一库公开读取、预览图编辑与发布缓存设计；未对生产后端、数据库、RunPod worker 或用户设备做性能剖析。
- **代码确定**指控制流能证实；**VM 复现**指真实客户端/主程序/元数据存储加可控网络或存储边界；**Chrome 实测**指隔离浏览器内真实 Vue、本地 HTTP 和真实 IndexedDB。
- Chrome 外网请求全部拦截，同源统一库使用空目录 fixture。无真实凭据、RunPod 请求、生成费用或生产资源写入。
- CPU 4 倍降速是实验条件，不代表真实手机；下面是小样本探针，不是统计性能保证。DOM 更新完成/图片 load 观测也不等于精确的屏幕首次绘制时间。
- 不把人工存储延迟当实际磁盘耗时，不把超时配置断言当真实计时，不把大参数压力样本当正常上传路径。

## 2. 已独立验证的主要发现

### R1 · 优先修正确性：取消发生在图片写入期间，终态仍可能被覆盖

位置：`js/main.js:5410–5444`、`:6383–6408`。

`finalizeHistoryEntry` 只在入口检查 CANCELLED，随后 `await putImages`，返回后无条件写 COMPLETED。真实任务/取消路径中把存储边界挂起，观测为：

```text
写图期间取消 → CANCELLED → 放行写图 → COMPLETED / images=1
```

这不是上次已修复的旧元数据快照回写问题，而是结果函数自己的跨 await 缺口。用户删除记录、切换查看对象也需要单独守卫，不能借加速重新插回已删除记录。

方向：结果写回前确认同一任务/记录仍有效、取消仍优先；图片清理只能清理确定未被历史/收藏/当前保留图引用的数据。不能无条件删除刚写的 id。

验收：在 /status、图片写入、元数据保存各阶段分别取消；解除边界等待后状态不复活、不冒出图片、不误删收藏，队列正常收敛。

### R2 · 用户可感知等待：图片展示和下一任务启动均依赖存储收尾

位置：`js/main.js:5427–5462`、`:5911–5918`、`:6067–6068`。

顺序为：HTTP 完整结果 → 写入整批图片 → 更新页面图片 → 保存/裁剪元数据 → runTask finally 释放槽位 → pumpQueue。

真实本地 HTTP 返回 4 张仓库 PNG，总响应 **3,270,424 bytes**，CPU 4 倍降速，无 Axios 替身：

| 条件 | HTTP responseEnd | 客户端结果可用 | put 开始/结束 | IDB 实际写入 | DOM 图片/图片 load 观测 |
|---|---:|---:|---:|---:|---:|
| 常态末次样本 | 32ms | 39ms | 42 / 59ms | 16ms | 87ms |
| 人工增加 500ms 存储等待 | 15ms | 24ms | 26 / 535ms | 8ms | 547ms |

所有值相对恢复开始；常态另一次 DOM 观测 94ms、实写 16ms，延迟实验另一次 570ms、实写 10ms。结论是**存储确实挡住展示**，不是“本机正常写盘就会卡几秒”。结果下载、JSON 解析、图片解码、主线程繁忙、S3 图片另行下载也可能贡献用户实际等待。

方向：先修 R1，再设计“及时展示 + 明确保存状态 + 安全持久化”的链路。**不可只把 await 删掉或简单把 updateHistoryEntry 挪到 putImages 前**：400ms 自动保存、刷新、收藏、删除、裁剪可能在图片真正落盘前运行。必须定义元数据何时可引用图片、未完成写入如何保护、保存失败如何提示、何时释放本地槽位。

验收：首图/图片 DOM 在慢保存结束前可用；保存失败不伪称已保存；保存中刷新有明确恢复语义；取消/删除/收藏/裁剪竞态不退化；排队无需等待不必要的页面收尾。不会因优化自动重提 Job。

### R3 · 低成本浪费：显式保存没有清除已排好的防抖保存

位置：`js/main.js:5141–5187`、`:5355–5365`、`:5462`。

完成更新先排 400ms timer，又立即 persistHistoryNow；后者没有清 timer。保留真实防抖与真实 HistoryStore 的独立探针：

```text
立即保存结束：save=1 / localStorage.setItem=2
500ms 后：    save=2 / localStorage.setItem=4
```

方向：显式保存接管对应待处理 timer，保持串行链、过期快照校验、三轮重试后重新排队和失败语义。清 timer 应发生在正确的入口时机，不能顺手吞掉保存过程中后来产生的更新。

验收：静止状态的一次完成只保存一轮；保存期间发生新变化仍会补存；超限裁剪、收藏和最终磁盘一致性保持。

### R4 · 取消后体感卡住：在途查询未中止，槽位尚未释放

位置：`js/main.js:5906–5931`、`:6383–6438`，`js/runpod-client.js:382–395`。

取消只置标记并尽力调用 /cancel，status 请求仍等待返回或单次超时，finally 才清理 activeJobs。独立 VM 复现：取消后记录已 CANCELLED，但挂起查询期间仍 active=1、queued=1，下一任务未启动。

方向：优先让本地在途查询可中止，使任务 Promise 尽快安全结束，由既有 finally 自然释放槽位，无需手工删除 activeJobs；区分**停止本地等待**与**远端确认取消**，保留原 Job 身份和迟到响应守卫。不能把“直接删除 activeJobs 并启动下一个任务”当无风险方案：远端任务未必停止，可能增加远端并发/费用。提交 /run 尚无 Job ID 的情形另行处理，不盲目丢失随后返回的 id。

验收：用真实本地 HTTP 挂起响应，取消后观察 XHR 中止、槽位及队列；迟到完成不复活，/cancel 失败不伪称远端已停止，提交阶段取消仍处理迟到 Job ID。

### R5 · 首次交互卡顿：空闲预加载不是非阻塞建索引

位置：`js/main.js:2966–2978`，`js/tag-index.js:175–227`、`:415–460`。

英文/中文 CSV 到达后，都在主线程单个任务内解析并建索引。实际仓库数据：112,476 英文标签、96,147 中文映射；两 CSV 原始总量约 7.09MB，非网络压缩传输量。

隔离 Chrome 三次样本：

| 条件 | 英文解析/建索引 | 中文解析/建索引 |
|---|---:|---:|
| CPU 原速 | 约 85ms | 136–139ms |
| CPU 4 倍降速 | 309–315ms | 586–605ms |

PerformanceObserver 记录到对应 long task。requestIdleCallback 只决定何时开始，不会把循环移出主线程。

方向：先分块调度并在块间真正让出主线程；Worker/预生成索引再按收益决定。`await Promise.resolve()` 只让出微任务、不保证渲染/输入机会，不能当已解决。保留加载 Promise 去重，全部索引构建完成后才发布 ready；不能让搜索读到半成品。

验收：真实大词库、加载期间持续输入与点击、首次中文/英文搜索、快速切词、失败重试；记录 long task 和输入响应，不只测搜索结果是否正确。

### R6 · 收起时仍干活：隐藏 Workflow 仍布局及生成执行 JSON

位置：`index.html:711–826`，`js/main.js:1951–1967`、`:2144–2145`、`:2344–2442`、`:2633–2639`。

面板、子页使用 v-show；renderWorkflowGraph 没判断面板是否收起。150 节点合成压力样本，CPU 4 倍降速，**容器不可见时仍新建 Cytoscape 并布局 260–264ms**。

隐藏的执行 JSON 仍触发 finalWorkflow 全量替换与格式化。正常内置 9 节点工作流，改 prompt 的 DOM 更新约 3–4ms；正常参数的 150 节点合成工作流约 8–13ms（2MiB 输入图片单独位于 inputImageData，执行 JSON 仅约 23KB）。因此不能把普通模板描述为严重瓶颈。

方向：折叠时不做布局，展开且处于 graph 页时补绘并保持节点选择/视口语义；执行 JSON 在需要展示/提交时计算。注意仅隐藏 pre 还不够：执行页按钮的 `:disabled="!finalWorkflow"` 也会提前消费该 computed。提交必须拿到最新参数，不得发送惰性缓存里的旧 workflow。

验收：折叠载入不布局、首次展开正常布局、切模板/改节点/LoRA 后图和执行 JSON 一致、提交使用最后一次 prompt/seed，频繁展开收起无画布泄漏。

## 4. 不采纳的捷径

- 不通过缩短轮询间隔、提高并发、延长所有超时来冒充普遍提速。这些会增加请求、资源占用或远端并发，不能缩短 worker 推理本身。
- 不静默丢图、不取消版本校验、不减少取消守卫、不自动重提未知提交。
- 旧快照签名在 save 返回后检查；save 内可能已经完成删图。元数据重存不能恢复已删 blob。当前没有独立证实健康单标签页因此稳定丢图，但“先显示后保存”设计必须考虑这个破坏性副作用。
- 自建存储操作队列不自动解决旧意图：必须在实际删除前确认引用/任务版本。新增串行链反而可能增加等待，应有明确收益证据。
- 不把 source 内重复的 data/dataURL 属性直接换算成“双倍内存”；字符串 rope/共享和图像解码缓存影响实际驻留，需要堆与图像内存测量。
- 统一库已有可见24项、详情并发2、请求去重、版本隔离与缩略图 lazy/async；不建议为提速改成无界详情预取。后端公开列表只读已发布元数据，保留事务快照、ETag 和鉴权边界。

## 5. 下一步建议（待确认实施）

1. **第一批：结果链路正确性与直接浪费。** 先加取消发生在写图期间的失败用例、补终态/记录有效性守卫；修显式保存和 timer 重复执行。再单独审定“展示与保存解耦”的状态/存储方案，不能凭一次代码挪动直接发布。

3. **第三批：调度与大图库。** 在途查询 abort、取消槽位语义、稳定状态降频、按需图片加载；总轮询预算/刷新状态文案另行确认产品取舍。

每一批遵守：失败复现 → 实现 → 另一方审核 → 自动化及真实浏览器关键路径 → 经授权提交发布。不能由实现者自己验收。
